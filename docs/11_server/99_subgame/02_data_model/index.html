      子游戏（SubGame）必须严格遵循以下架构模型进行设计与编码. 各模块应保持明确的职责边界.

      模块概述#

      子游戏由以下四个核心模块组成：

      • TableSink: 子游戏入口, 负责模块组织与外部交互
      • Data: 数据层, 负责维护子游戏的数据状态
      • Flow: 逻辑层, 负责业务逻辑
      • MessageHandler: 负责Sub消息协议分发与处理

      数据模型设计#

      TableSink#

      职责：

      • 继承TableBase, 是子游戏桌子的入口
      • 持有并管理 Data, Flow, MessageHandler 三个模块

      设计约束:

      1. 除了模块之外, 不应该持有任何数据

      Data#

      Data 是子游戏数据的唯一权威来源，负责维护:

      • table数据: 游戏状态, 棋盘, 当前行动方等
      • 玩家数据: 玩家在游戏过程中产生的数据(不维护玩家信息UserInfo)

      设计约束：

      1. 所有内部数据字段均为私有字段
      2. 所有数据写入均通过setter
      3. Setter负责校验数据是否可写入, 忽略不合法的数据
      4. 对外提供只读查询接口，必要时返回副本，避免外部直接修改内部数据
      # 例如，修改当前行动方时：

public:
void set_turn_chair(int chair) {
  if (chair > 100) return;
  turn_chair_ = chair;
}

void turn_chair() {
  return turn_chair_;
}

private:
 int turn_chair_  = -1

      Flow#

      Flow 负责实现子游戏的完整业务流程, 是游戏业务逻辑的唯一执行入口
      Flow 的设计应以业务流程图为依据

      设计约束：

      1. Flow 持有 Data 的引用, 不自行维护第二份对局状态

      2. 所有业务操作先进行必要的合法性校验

      MessageHandler#

      MessageHandler 负责消息协议的分发与处理, 继承子游戏消息协议中的 sub_handler

      设计约束:

      1. MessageHandler 持有Flow的引用
      2. MessageHandler 不持有任何自己的数据

      MessageHandler 的主要作用是解耦 消息协议与Flow. 让Flow可以专注游戏流程本身

      核心设计: flow#

      Flow 的设计以游戏业务流程为依据, 通过状态图和业务流程图共同描述游戏逻辑.

      1. 状态图: 描述游戏的生命周期、游戏状态以及状态转换条件
      2. 业务流程图: 描述业务事件触发后, Flow 的执行步骤、判断分支、数据变更以及流程结束条件

      设计原则:

      1. 先根据 业务事件 绘制出 总的业务流程图
        这里的业务事件是指游戏领域中的业务动作, 不等同于 Sub 消息协议
        Sub 消息只是触发业务动作的一种外部途径. 业务动作也可能由定时器、系统事件或其他内部逻辑触发
      2. 根据业务流程图总结出 状态图 (一般可以省略)
      3. 根据业务事件确定Flow 的 业务函数
        业务函数是对游戏业务动作的封装.
        业务函数不一定是public
        业务函数可以包含多个内部函数.
        复杂业务函数可以有自己的 二级业务流程图
      4. 根据状态图确定 GameStatus, 并使用 GameStatus 约束业务函数
      flowchart TD
    A[游戏规则] --> B[业务事件梳理]
    B --> C[总业务流程图]
    C --> D[提取业务函数]
    D --> H[二级业务流程图]
    H --> I[细化内部函数]
    I --> J

    C -.-> E[梳理状态图]
    E -.-> F[确定 GameStatus]
    F --> G[约束业务函数]
    G --> J[Flow 实现]
